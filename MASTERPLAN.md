# Incremental Worker-Process Migration Plan

No implementation files should be changed while this document and its linked OpenSpec changes are under review. The plan below treats every numbered item as a small, independently testable commit.

## Target State

### Standard mode — default

```text
Container
├── Web/control process
│   ├── Blazor WebUI
│   ├── scheduler
│   ├── lightweight work detector
│   └── worker launcher/progress bridge
│
└── temporary worker process
    ├── processing pipeline
    ├── Overture/GADM services
    ├── country index
    └── exits after the run
```

### Web-only mode

- WebUI remains available.
- Internal scheduling is disabled regardless of schedule settings.
- Manual processing, Lookup, and Data operations launch workers.

### Run-once mode

- No Web server.
- Checks for eligible assets, processes them, and exits.
- Intended for cron, Docker Compose jobs, and external schedulers.

### Internal worker role

Not a public deployment mode. The Web process launches the same application assembly with an internal worker argument. No Docker socket or second image is required.

## Core Design Decisions

1. **Same image and assembly initially.**  
   Role selection happens before building either the Web or worker host.

2. **The worker is a separate OS process.**  
   Process exit is what reliably returns managed and native memory.

3. **Web remains the control plane.**  
   It owns scheduling, UI state, progress display, and job arbitration.

4. **Worker owns all heavy geodata operations.**

5. **Communication uses redirected standard streams:**
   - `stdout`: versioned NDJSON events only;
   - `stdin`: request and cancellation commands;
   - `stderr`: ordinary worker logs.

6. **Only one heavy worker runs at a time.**  
   The Web process has a local coordinator; workers also use a PostgreSQL advisory lock to protect against external run-once processes.

7. **Existing installations remain Standard mode by default.**

8. **No Immich schema modifications in this change.**

9. **No geometry-algorithm redesign in the initial worker migration.**  
   Candidate-only geometry loading can follow after process isolation is stable.

# Phase 1 — Lock Down Existing Behavior

### 1. `test: characterize empty scheduled processing pass`

**Purpose**  
Freeze the no-work execution path before Phase 2 separates scheduling from execution.

**Current baseline**  
The due-schedule branch in `ProcessingBackgroundService.ExecuteAsync` acquires `_runLock`, calls `ProcessingState.MarkPending()`, and invokes private `RunOnceAsync`. `RunOnceAsync` first awaits the exact `ImmichDbRepository.GetUnprocessedCountAsync` query (eligible rows have null city and country, non-null GPS, and a non-deleted asset), then calls `StartRun(total)`. For `total == 0`, it logs `Run started — nothing to process, all assets already have location data.` and returns through `finally`, which calls `CompleteRun()` and appends `Run complete. Processed=0 Skipped=0 Errors=0`. The skipped-ID load, config read inside the non-empty branch, batch fetch, asset resolution, airport lookup, skipped/write operations, and counter increments are not reached. Existing `ProcessingPipelineTests.cs`, `ProcessingStateTests.cs`, and `SkippedAssetsRepositoryTests.cs` do not execute this service path.

**Planned change**  
Add a narrow internal pass-invocation/collaborator seam while leaving the public DI constructor and production call order unchanged. Exercise the same pass method called by the scheduler with a zero-returning count spy and fail-fast unused collaborators. This block characterizes execution after scheduled admission; cron timing, `_runLock`, `MarkPending()`, skipped-database startup initialization, and the later work-detector abstraction remain out of scope. “No geodata work” means no operation call, not that DI never constructs those singleton services.

**Edge cases and decisions**  
“Empty” is exactly a count of zero, not a future existence probe; the count can include IDs present in `skipped.db` because skipped IDs are loaded only after the zero gate. Cancellation/count-query failures and duplicate-trigger arbitration are not empty passes and belong to later lifecycle coverage. Assertions ignore wall-clock log prefixes but preserve the two empty-run messages and their order.

**Acceptance and verification**  
A focused MSTest proves one count call; zero processing-configuration, skipped-ID, batch, resolver, airport, skipped-write, and location-write calls; `TotalUnprocessed == 0`; processed/skipped/error counters remain zero; `IsRunning == false`; `LastError == null`; start/completion timestamps are set; and the nothing-to-process line precedes the zero summary. Run `dotnet test --project tests/ImmichReverseGeo.Tests/ImmichReverseGeo.Tests.csproj --filter <empty-pass-test>` and `npm run test` with default exclusions.

**Dependencies and sequencing**  
First Phase 1 block; keep its internal seam narrow so blocks 2 and 3 can reuse or replace it without creating the Phase 2 executor early. It must precede Phase 2’s executor extraction and Phase 5’s empty-schedule worker gate.

### 2. `test: characterize processing lifecycle transitions`

**Purpose**  
Protect current admission, single-run ownership, and terminal cleanup before a coordinator and worker protocol replace in-process control flow.

**Current baseline**  
`ProcessingBackgroundService` owns a nonblocking `SemaphoreSlim _runLock`, manual-only `_runCts`, and private `RunOnceAsync`. The due-schedule branch calls `WaitAsync(0, stoppingToken)`, immediately calls `ProcessingState.MarkPending()`, awaits the pass, and releases the lock in `finally`; contention appends exactly `Scheduled run skipped because a processing pass is already in progress.` `TriggerRunAsync` calls `Wait(0)`, returns a completed task silently on contention, marks pending, and dispatches fire-and-forget work whose `finally` releases the lock. `MarkPending` and `StartRun` both expose `IsRunning=true`, but only `StartRun` resets counters/error and sets the start timestamp after the eligibility count. The outer pass catch logs `Run cancelled.` for token cancellation or records a fatal error with `IncrementError`; its `finally` always calls `CompleteRun` and logs the summary. `CancelRun` targets manual runs only because scheduled execution never assigns `_runCts`. Existing tests do not invoke this service or cover admission, cancellation, failure, lock recovery, or retriggering.

**Planned change**  
Reuse block 1’s internal operation/pass seam and add the narrowest internal scheduled-admission entry used by the real due-schedule branch; do not add a clock, cron, coordinator, or executor abstraction. Drive the exact count and the first post-`StartRun` operation with `TaskCompletionSource`-backed delegates so tests can observe pending before the count completes, active execution after `StartRun`, and terminal cleanup without sleeps or real PostgreSQL, SQLite, geodata, or scheduler delays. Characterize successful completion, manual `CancelRun` cancellation after `StartRun`, and a pass-level exception reaching the outer failure catch. While each run is held, prove a duplicate manual trigger is silent and a duplicate scheduled admission logs the current skip message. After success, cancellation, and failure, await explicit pass return and admission-owner release, then prove lock recovery by admitting later manual and scheduled work; an inactive terminal snapshot alone does not establish availability. Keep terminal outcomes inferred from state/logs; do not introduce an outcome enum or normalize contention behavior.

**Edge cases and decisions**  
Lifecycle cases intentionally cross `StartRun` so stale pre-start counters from an earlier run are not made part of this contract. Cancellation means the current manual CTS path at an awaitable operation boundary; scheduled host-token cancellation, per-asset cancellation swallowing, synchronous native interruption, cron timing, and `TriggerRunAsync` becoming awaitable remain out of scope. Tests observe `LastRunStarted`, `LastRunCompleted`, counters, `LastError`, stable log content/order, operation counts, and subsequent admission rather than private lock fields or notification counts.

**Acceptance and verification**  
Signal-based MSTests prove pending has no start timestamp, active execution has a start timestamp, every terminal path is inactive with a completion timestamp, cancellation logs without an ordinary error, failure exposes the thrown message and fatal log, each duplicate starts zero extra passes, scheduled contention alone emits the skip log, and both trigger origins can be admitted after every pass has returned and released admission ownership. ### 4. `fix: disable pooling for temporary Overture export databases`

**Purpose**  
Remove the confirmed one-shot SQLite pooling defect before repeated exports are moved across process boundaries.

**Current baseline**  
`OvertureDivisionCacheService.DownloadDataInternalAsync` creates `{ISO3}.{GUID}.tmp`, calls private `ExportOvertureDivisions`, validates the file, and moves it to `{ISO3}.db`; its catch deletes the temporary file. Inside the exporter, the DuckDB reader is an in-memory using scope, but the SQLite output at `OvertureDivisionCacheService.cs:232` opens with only `Data Source`. `Close()` and `SqliteConnection.ClearPool(sqlite)` run only after commit, so any DDL, metadata, row-copy, or commit fault after `Open()` bypasses the pool clear; disposal can return the native connection to a pool keyed by a GUID path that will never be reused. Microsoft.Data.Sqlite 10.0.11 supports `SqliteConnectionStringBuilder.Pooling` and pool clearing but exposes no public pool count. Existing Overture read/validation paths and the GADM exporter already disable pooling; DuckDB has no evidenced pool in this path and is outside the defect boundary.

**Planned change**  
Create the temporary output connection through one internal helper using `SqliteConnectionStringBuilder { Pooling = false }`; change no other connection, schema, query, or publication step. Keep both public constructors/DI behavior intact and add an internal exporter-operation seam for tests. A controlled exporter opens the exact helper connection, throws immediately after open on repeated unique paths, then on a repaired retry writes a minimal valid one-row database so the real cleanup, validation, move, and ready-state logic runs without Azure or DuckDB.

**Edge cases and decisions**  
Use the exact connection's parsed `Pooling == false` plus removed temp/final-file state as the deterministic provider-supported oracle; do not use RSS, timing, reflection into provider internals, or cross-platform file-lock behavior. Before-open failures create no SQLite pool and are not the regression. Post-open DDL/metadata/copy/commit failures must fault, delete `*.tmp`, and publish no final cache. Zero-row and invalid-file branches retain their existing cleanup. A repaired same-country retry must use a new GUID path and may publish only after validation. Preflight/stale in-flight retry races belong to block 5; cancellation of synchronous native work belongs to block 6. Preserve same-country active-download sharing.

**Acceptance and verification**  
Focused MSTests repeat the post-open failure with distinct paths, assert each exact output connection has pooling disabled, every task faults, all failed temps disappear, and `CHE.db` is absent; after disabling the injected fault, a new path publishes `CHE.db`, `HasData("CHE")` is true, and row/release metadata is readable. Run `for i in 1 2 3 4 5; do dotnet test --project tests/ImmichReverseGeo.Tests/ImmichReverseGeo.Tests.csproj --filter "FullyQualifiedName~OvertureDivisionCacheServiceTests" || exit 1; done`, then `npm run test` with default exclusions.

**Dependencies and sequencing**

### 5. `fix: always remove completed cache download tasks`

**Purpose**  
Ensure every terminal country-cache task releases its in-process coordination entry so later Overture and GADM requests remain retryable before extraction or worker orchestration relies on them.

**Current baseline**  
`OvertureDivisionCacheService` and `GadmDivisionCacheService` each own a singleton-scoped `ConcurrentDictionary<string, Lazy<Task>> _inflightDownloads` plus a positive ready-cache set. `GetOrStartDownload` performs an outer `HasData` readiness check before map insertion, then inserts/evaluates a per-country lazy whose task repeats `HasData`. In each internal task, that repeated preflight and source-specific path/setup work occur before the current try/finally; an exception there can strand the faulted lazy. Overture’s protected region owns its `*.tmp` export cleanup, while GADM’s also owns `*.gpkg.download` cleanup. `EnsureDataAsync` conditionally removes a completed entry in a caller-side finally, but `AdministrativeAreaResolverService.ResolveOvertureAsync` and `ResolveGadmAsync` call `GetOrStartDownload` and `WaitAsync` directly. All removals are currently key-only, so delayed cleanup can remove a newer same-country value. Existing unit tests cover status/deletion; resolver fixture tests use ready caches; GADM integration tests exercise live success. None characterizes task ownership, early faults, cancellation, or concurrency.

**Planned change**  
Make the map own each winning lazy from insertion through the complete source task body. Wrap the whole inner operation—including its repeated readiness preflight and pre-try setup—in terminal cleanup, and remove the entry by exact key/value identity using atomic compare-remove semantics. Remove caller-side ownership from `EnsureDataAsync`; direct resolver callers and wrapper callers then share the same lifecycle. Preserve source-specific temporary-artifact handling, public constructors/DI, cache validity, publication, resolver ordering, and the existing first-owner-token/shared-task behavior. Add narrow internal source-operation seams, defaulting to the existing Overture and GADM operations, so tests can control task start and terminal outcome with `TaskCompletionSource` gates without Azure, GADM downloads, DuckDB, SQLite timing, or sleeps.

**Edge cases and decisions**  
The outer ready-cache preflight happens before any entry exists; if it throws, a later call is already free to retry. The cleanup defect boundary starts once a lazy is inserted and includes the inner `HasData`, country mapping, directory/path setup, transfer/export, validation, and publication. Success, fault, and shared-task cancellation must each release only their own value. A non-owner caller cancelling only its `WaitAsync` must not evict or cancel still-active shared work; later callers continue to join it. A valid cache returns `AlreadyReady` without creating work. Concurrent unavailable-cache callers receive the same active task, with exactly one reported starter and remaining callers reported as awaiters. Overture keeps `*.tmp` cleanup and block 4’s non-pooled exporter seam; GADM separately keeps `*.tmp` and `*.gpkg.download` cleanup. Broader cancellation propagation and source exception normalization remain block 6.

**Acceptance and verification**  
Deterministic source-specific MSTests prove: an inner preflight/operation fault followed by repair starts a new same-ISO3 task; owner-task cancellation is retryable; success releases ownership and an already-published cache short-circuits; simultaneous callers share one exact task and invoke source work once; cancelling one waiter leaves the active entry joinable; and an old completion/removal cannot delete a replacement lazy for the same key. Use handcrafted valid-cache fixtures only for ready/publication behavior and gates for lifecycle ordering. ### 6. `fix: preserve cancellation through geodata operations`

**Purpose**  
Establish a correct in-process cancellation and critical-failure baseline across active Web, Overture, and GADM geodata work before later worker protocols transport those outcomes.

**Current baseline**  
The run token flows from `ProcessingBackgroundService` through per-asset administrative resolution, shared country-cache waits, provider lookups, and optional infrastructure resolution, but token acceptance does not imply observation. `ProcessAssetAsync` catches active-token `OperationCanceledException` and returns, while `RunOnceAsync` labels every `OperationCanceledException` as cancellation even when its run token is not requested. `AdministrativeAreaResolverService.ResolveGadmAsync` converts every exception into cache unavailability/territory fallback; Overture place, infrastructure, and division lookups and GADM single/multi-cache lookups convert broad failures into diagnostics; release discovery, cache status/readiness/validation, metadata, and Web cache helpers also retain deliberate fallbacks behind broad catches. `OvertureDataAccess.TryGeometryContains` and GADM cached-candidate containment return geometry false for every exception, including `OutOfMemoryException`. Overture bundled-country corruption instead fails index loading; malformed GADM cached WKB sets geometry false but remains eligible for existing bounding-box fallback/ranking; malformed GADM source GeoPackage/header/WKB fails cache construction. Cached/bundled fast paths can return without checking a pre-cancelled token, GADM synchronous SQLite lookup does not observe its token internally, and an owner-cancelled shared task is not necessarily cancellation of another live waiter.

**Planned change**  
At each active token-bearing entry, diagnostic catch, native boundary, and result/publication boundary, distinguish cancellation requested by the current caller token from an unrelated `OperationCanceledException`. Rethrow current-caller cancellation, including from per-asset processing, so the existing run cancellation log/cleanup executes; classify an unrelated OCE as ordinary dependency failure/source unavailability rather than a cancelled run. Preserve block 5’s first-owner and exact-value cleanup contract: a non-owner cancels only its own `WaitAsync`, while owner-task cancellation is ordinary source unavailability to a live waiter whose token remains active. Propagate `OutOfMemoryException` unchanged across active geometry, lookup, release, cache probe/status/validation, export, metadata, resolver, and Web-helper catches, but do **not** require every exception to propagate: existing non-cancellation/non-OOM HTTP, SQLite, I/O, release, cache-unavailable, diagnostic, and territory fallbacks remain intentional. Limit malformed-geometry tolerance to recognized per-candidate WKB/topology failures: Overture cached-division and bundled-infrastructure candidates may become geometry false; bundled-country artifact corruption remains fatal; GADM cached candidates retain geometry-false plus bbox fallback/ranking; malformed GADM source artifacts remain export/build failures with temp cleanup and no replacement of a prior cache. Lookup and GeoBoundaries keep their current default/non-cancellable UI token flow; adding component-owned cancellation is out of scope.

**Edge cases and decisions**  
Cancellation is cooperative. Check before and after synchronous DuckDB/SQLite, filesystem, and NetTopologySuite regions, between practical managed rows/layers/candidates, and immediately before success or cache publication. An already-running native call or `Task.Run` delegate is not preemptible; cancellation is observed at the next managed checkpoint. Cancellation after export but before move deletes the temporary output and publishes nothing. Add only narrow internal controlled-throw/checkpoint seams, reusing blocks 4–5 exporter/source-operation seams and leaving public constructors/DI unchanged. Use `TaskCompletionSource` gates with asynchronous continuations and injected active OCE, unrelated OCE, ordinary exception, OOM, and malformed bytes; never use live-source timing, sleeps, actual memory exhaustion, or native interruption as an oracle. Block 6 uses current logs/state/writes, not block 7’s future typed outcome model.

**Acceptance and verification**  
Deterministic Web tests prove active run-token cancellation produces the existing `Run cancelled.` signal and terminal cleanup with no ordinary/per-asset error, skipped record, or location write, while unrelated OCE is failure; resolver tests preserve ordinary territory fallback while active cancellation and OOM escape. Overture/GADM tests cover pre-cancelled warm/bundled/cached returns; active versus unrelated OCE; owner, non-owner waiter, and foreign owner-task cancellation; controlled OOM at lookup/geometry/release/cache/metadata catches; post-export/pre-publication cancellation with cleanup/no move; ordinary diagnostic fallbacks; tolerant Overture candidate corruption versus fatal bundled-country corruption; GADM cached-WKB bbox behavior versus fatal malformed source export. # Phase 2 — Extract the Processing Executor

### 7. `refactor: introduce processing run request and result models`

**Purpose:** Establish immutable, transport-neutral facts for one accepted processing run before reporter and executor extraction.

**Current baseline:** `src/ImmichReverseGeo.Web/Services/ProcessingBackgroundService.cs` owns triggering, nonblocking admission, execution, cancellation, and terminal logging; `ProcessingState` owns mutable WebUI lifecycle, counters, logs, and activity state. Its `ProcessedThisRun` counter currently means successful location writes, and its error counter combines per-asset errors with a fatal pass error. There is no immutable run identity, no separate attempted-versus-updated accounting, and no result value returned by execution.

**Planned change:** Add dependency-light immutable contracts in Core: `ProcessingRunRequest(Guid RunId, ProcessingRunTrigger Trigger)`; `ProcessingRunResult` carrying that request, `DateTimeOffset StartedAtUtc`/`EndedAtUtc`, non-negative `long` processed/updated/skipped/failed counts, `ProcessingRunOutcome`, and failure detail only for a failed outcome. Trigger vocabulary is exactly `Manual`, `Scheduled`, and `RunOnce`; worker execution is not a trigger. Outcome vocabulary is exactly `Completed`, `Cancelled`, and `Failed`; an empty pass and a pass with handled per-asset failures still complete, cancellation is not failure, and only a pass-level fatal error fails the run. Every accepted run gets one non-empty, unique `Guid`; a rejected duplicate gets no request/result. Both timestamps must have zero UTC offset and completion cannot precede start. `ProcessedCount` means assets that reached one per-asset terminal disposition and must equal `UpdatedCount + SkippedCount + FailedCount`; `UpdatedCount` alone means successful Immich location writes. Previously suppressed IDs and cancellation-interrupted assets are not processed. A fatal run outcome does not itself increment the per-asset failed count. Preserve the WebUI by continuing to map its existing “processed” display to successful writes rather than adopting the new aggregate meaning in this block. **Firm:** no service wiring, behavior, schedule, persistence, UI, reporter, executor, coordinator, protocol, serialization, or mutable history/state change.

**Acceptance and verification:** Focused contract tests cover every trigger/outcome, non-empty identity, immutable field preservation, UTC/order/count/failure-detail invariants, empty and partial terminal summaries, and invalid construction. Existing Phase 1 lifecycle/state tests and the normal default-exclusion suite remain regression verification. All four OpenSpec artifacts must be coherent and `openspec validate 07-introduce-processing-run-request-result-models --strict` must pass.

**Dependencies and sequencing:** Blocks 1–6 are ordered planning context and are not assumed implemented; apply and verify them before this block. ### 8. `refactor: introduce processing event reporter`

**Purpose:** Define the UI-independent processing event language needed to remove the pipeline’s direct WebUI-state dependency without creating a behavior gap before the state adapter exists.

**Current baseline:** `ProcessingBackgroundService` directly owns `ProcessingState` lifecycle, updated/skipped/error counters, bounded UI logs, completion, and a nested `ProcessingResolutionProgress` bridge; scheduling/startup logs, `MarkPending()`, `_runLock`, and the manual CTS are control-plane concerns. Assets run concurrently. `ProcessingState` reference-counts activity labels and synchronously notifies Blazor consumers. Block 7 defines request/result identity, UTC timing, aggregate `ProcessedCount == UpdatedCount + SkippedCount + FailedCount`, successful-write `UpdatedCount`, per-asset failures, and completed/cancelled/failed outcomes, but those source models must be applied before this block.

**Planned change:** Add a dependency-light asynchronous `IProcessingEventReporter` that opens an unwired, validating run-scoped session. The immutable vocabulary is run started, eligibility determined, coherent progress changed, correlated activity started/ended, typed log emitted, and run finished; every event identifies the block-7 request and finish carries its validated result. The session serializes concurrent calls, owns disposition accounting and activity identities, enforces lifecycle order/finality, and makes those producer rules testable without production wiring. ## Final Acceptance Criteria

The change is complete when:

- Exact `IMMICH_REVERSEGEO_MODE` values `standard`, `web-only`, and `run-once` select Standard, Web-only, and Run-once from one neutral image; only an absent value defaults to Standard, and every other present value fails before host construction with exit 2.
- Standard remains the backward-compatible default, and mode selection is startup-only, restart-required, and not persisted.
- WebUI remains available in Standard and Web-only modes.
- Standard scheduled checks use the full current-eligibility `EXISTS` predicate and do not launch workers when it reports no work; no watermark, incremental tail, reconciliation cadence, or NAS-specific control is shipped.
- The Web process cannot initialize heavy geodata services.
- Processing, Lookup, and heavy cache work run in temporary workers.
- Verified temporary-worker finality reaches process exit, stream drain, owned-resource cleanup, and local admission release; memory claims remain bounded to measured environments.
- One Standard/Web-only Web control plane admits at most one local exclusive heavy job or coordinated maintenance owner; ProcessAssets additionally uses the PostgreSQL advisory lock across processes, without claiming distributed exclusion for Lookup/cache work.
- Progress, logs, cancellation, failure, and crash recovery remain visible in WebUI.
- Run-once performs one direct non-Web attempt without starting ASP.NET, spawning a child, or applying a detector precheck.
- Repeated-worker evidence proves fresh worker processes, complete finality, no surviving descendants or owned temporary artifacts, and no heavy-geodata initialization in Web; no universal RSS plateau or threshold is promised.
- Public and maintainer documentation cover the new operational model.
