# Accepted worker events and UI notifications

Change 65 adds bounded delivery after the existing v1/v2 stdout codec, framing, correlation and exact-sequence validation. Every raw frame is still validated. The emitter, wire bytes, public settings, process stop grace and result classifier retain their existing contracts.

Only the canonical ProcessAssets descriptor declares absolute progress counts replaceable. Lookup and cache progress describe steps, so their events stay lossless. Each accepted stream owns one delivery scope, one consumer, a lossless FIFO with 256 entries, and one replaceable latest snapshot. Lossless events seal the preceding snapshot into their FIFO entry. The consumer delivers that snapshot before its barrier. Retained inputs are therefore bounded by `2 * capacity + 1` in the buffer, plus at most two in the consumer and one in a waiting producer. This is an object-count bound, not a claim that the whole process uses constant memory or 257 events in total.

The FIFO waits asynchronously when full. It cannot drain unlimited lossless traffic faster than its consumer. Stderr and process-exit observers remain independent. Consecutive pending snapshots can replace each other without waiting; a fast consumer may still project most snapshots.

Each delivered event retains its source sequence. The queue authenticates the exact in-flight envelope and its contiguous replacement range. Copies, old scopes and unexplained gaps cannot advance the bridge. ProcessAssets also checks that the absolute count advanced by exactly the number of accepted dispositions. Capability clients recreate a transport context with the admitted identity; the adapter compares its version/kind/ID/origin values, binds the opaque delivery scope once, and retains the original lease context and page generation in its projection closure.

An accepted terminal closes intake before waiting for capacity. Earlier snapshots and lossless events drain first, terminal projects last, and the session joins delivery before evidence and settlement release admission. A terminal that wins acceptance is not replaced by later abandonment. EOF and failed/forced-stop cleanup do not fabricate a terminal. Repeated disposal joins one task, wakes waiters and joins in-flight projection. Ordinary cooperative Stop retains the existing worker grace period. Fault containment closes stdin while allowing valid output to drain: a failed write or flush does not prove that the worker rejected the command. Projection failure, disposal and forced-stop escalation can abandon undelivered work through their established paths.

## Notification boundary

ProcessingState, worker status, Lookup and cache controllers retain separate owners. Their ordinary notifications use a 100 ms TimeProvider cadence, with one dirty revision and at most one pending dispatch while a subscriber is busy. State mutations remain available to readers immediately. A timer is created only after the first dirty revision. Renderer callbacks run outside projection and ownership locks.

Terminal and classified final-state mutations request immediate dispatch and cancel a redundant ordinary notification for the same revision. A pending final keeps its priority when a newer ordinary revision arrives. Acceptance means that bounded asynchronous dispatch has been accepted; it does not wait for a Blazor renderer to finish. Lookup/cache terminal observation and later classified completion are distinct revisions, and each can request a final notification. Dashboard database-stat loading and cache-list reloads may also render separately. There is no promise of one physical render batch for an entire operation.

Page/controller generations and component disposal guards reject stale work. New components read current state directly. Tests can inject capacity and cadence; direct legacy constructors preserve their existing characterization behavior. Production Web factories and supported worker-session sinks select the measured defaults. There is no public switch, environment variable or protocol field for this policy.

Internal observations contain numeric counts, timing, queue bounds and a closed finality enum. They contain no messages or job identifiers. Metric names, exporters, dashboards and alerts belong to Change 66.

## Measurement and verification

The initial decision used 12 real child-process trials on an Apple M3 Pro with 36 GiB RAM, macOS 26.5.2, .NET 10.0.11, Arm64 and 11 visible processors. Trials sent 1,000 or 10,000 snapshots through raw validation, the actual session and bridge, ProcessingState and a real Logs renderer. They included 262,177 stderr bytes; the interleaved shape added activity start/end and four log levels every 100 snapshots.

For 10,000 snapshots, the initial end-to-end duration was 224–387 ms, FIFO high-water was 1–4, no capacity wait occurred, and terminal delivery took 0–1 ms. Ordinary notifications numbered two or three, followed by one final notification. Parent managed allocations were approximately 57–82 MB and included raw decoding and setup. Full-GC live managed deltas were small relative to allocations but include runtime/fixture effects; neither these deltas nor the parent-only measurements establish a child/native RSS or NAS hardware bound. These measurements support retaining 256/100 as bounded initial values, not an optimal-capacity claim.

Run `npm run agent:test -- --filter 'TestCategory=Change65'` for the focused suite. The measurement cases write separate JSON files to `_out/worker-event-delivery-measurements/`, including environment, selected policy and per-trial observations. Controlled capacity-one tests separately prove replacement, lossless backpressure, terminal ordering, cancellation and fault cleanup. Raw invalid-frame tests preserve primary failures; component tests use virtual time and held renderers. Full default tests and the worker CI matrix also protect existing lifecycle, composition and protocol contracts.
