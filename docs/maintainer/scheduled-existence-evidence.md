# Scheduled eligibility query evidence

Standard scheduled processing uses one `SELECT EXISTS` statement before run identity creation and admission. `ImmichDbRepository.HasUnprocessedAssetsAsync` owns the read; `ExistenceProcessingWorkDetector` maps its boolean to the existing detection result. The predicate matches the separate exact count used by Dashboard and worker execution: both city and country are null, both GPS coordinates are present, the asset is not soft deleted, and its EXIF row exists. Empty strings remain populated values. State and the local skipped store are outside this database predicate.

A positive observation can become stale before the worker obtains its own lock and exact count. A negative observation closes that scheduled occurrence; later work waits for an ordinary later trigger. Query failures and cancellation propagate through the existing pre-admission handling. The query introduces no retry, fallback, persisted state, setting, or schema change.

The repository passes the same cancellation token to connection opening and scalar execution, requires a boolean result, and disposes both connection and command. It leaves the existing Npgsql data-source command timeout unchanged. Npgsql documents scalar execution as returning the first column of the first row, so an unexpected or absent scalar is treated as an error. [Npgsql command API](https://www.npgsql.org/doc/api/Npgsql.NpgsqlCommand.html).

PostgreSQL can stop an EXISTS subquery after finding a qualifying row. A no-match query may still examine all relevant rows; neither fixed execution time nor a particular index is guaranteed. [PostgreSQL 16 subquery expressions](https://www.postgresql.org/docs/16/functions-subquery.html).

## Schema witness and fixture limits

The pinned upstream witness is Immich v3.2.0, commit `1b6098c9dbfffe978bec2d414606ed7a4c8e019a`: [asset table](https://github.com/immich-app/immich/blob/1b6098c9dbfffe978bec2d414606ed7a4c8e019a/server/src/schema/tables/asset.table.ts) and [EXIF table](https://github.com/immich-app/immich/blob/1b6098c9dbfffe978bec2d414606ed7a4c8e019a/server/src/schema/tables/asset-exif.table.ts).

The fields used by this query match the isolated PostgreSQL test schema: UUID asset primary key, EXIF assetId primary/foreign key, nullable city/state/country, nullable double-precision coordinates, and nullable deletion timestamp. Production declares additional columns and indexes, including a city index and a geographic expression index; the minimal fixture retains only its primary-key indexes. This is a query-schema witness, not a declaration of overall application compatibility or an index recommendation.

`ProcessingWorkDetectionPostgresTests` compares EXISTS with an independent exact count across eligibility cases and verifies both tables retain their logical row values. Its connected scheduled tests use real PostgreSQL reads, detector, coordinator and executor while substituting child transport and advisory-lock I/O. They cover a skipped-only eligible set and eligibility disappearing before the worker count. Failure tests exercise cancelled opening, missing schema/database, and a real command timeout behind a granted conflicting table lock.

`ScheduledExistencePostgresPlanTests` is explicitly tagged Integration and Performance. Normal runs exclude it. Its early-match, late-match and no-match fixtures each insert 10,000 rows; those names describe insertion position, not a promised access or join order. It executes the exact production statement with EXPLAIN ANALYZE, BUFFERS and JSON output, checks boolean parity and unchanged row values, and writes unique diagnostic JSON under `_out/postgresql-plans/change58/`. The evidence records server version, fixture assumptions, actual fixture indexes and the complete plan. Tests assert no plan node, index name, cost, timing, buffer count or speedup ratio. EXPLAIN ANALYZE executes the statement; these fixtures use isolated test-owned SELECT queries. [PostgreSQL 16 EXPLAIN](https://www.postgresql.org/docs/16/sql-explain.html).
